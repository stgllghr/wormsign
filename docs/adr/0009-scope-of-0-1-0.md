# ADR 0009: The scope of 0.1.0

- **Status:** Accepted
- **Date:** 2026-10-15

## Context

0.1.0 ships seven commands, the Action, `harden-dev.sh` (1,477 lines of bash), 11 SIEM detections in `detections/`
and an agent skill, kept by one maintainer, best effort. Reviewers read that as three products for one person. The
evidence behind each part differs:

- **`soak`, `diff`, `scan`:** a measured latency study, wave replays, a false-positive corpus and mutation-tested
  rules ([validation.md](../validation.md)).
- **`harden-dev.sh`:** tested against stub package managers under every bash the suite finds, and against real pip
  and uv on request.
- **The agent skill:** eight runs in headless Claude Code (run 5 twice) and a run without it
  ([evidence](../evidence/skill-eval.md)); Codex and Cursor have format checks only.
- **Detections:** never run on real logs or in a SIEM
  ([what is not validated](../../detections/README.md#what-is-not-validated)).
- **Workflow rules:** three of the seven overlap zizmor's audits, by its docs
  ([table](../positioning.md#the-workflow-rules-against-zizmor-and-actionlint)).

## Decision

**Keep every part, and label each one's maturity** ([stability.md](../stability.md#maturity)): stable, beta or
experimental, by the evidence behind it. What a part promises follows its label.

The breadth is deliberate. The parts answer one threat at each stage: `soak` and `diff` keep a worm's version out,
`scan` and `harden-dev.sh` find it on a machine and close what it uses, the detections, `audit-org` and the
incident-response guide catch it spreading, and the skill carries the same rules to coding agents. Cutting a part
would not make another better validated; labelling it says what is.

- All seven workflow rules stay; positioning.md shows the overlap and recommends running zizmor beside the gate. It
  is not part of the gate.
- [ADR 0005](0005-no-runtime-dependencies.md)'s question, a vendored YAML parser for the workflow reader, stays open.

## Consequences

- The surface to maintain stays as it is. A part whose evidence lags is labelled, not cut, and moves up a label
  when its evidence does (the detections first, through the real-log and SIEM item in the
  [ROADMAP](../../ROADMAP.md#next)).
- A part can still move out or be retired later, by the rules in [stability.md](../stability.md#how-a-change-is-made).
- A reader judges each part by its own label, not the project by its weakest part.

## Alternatives considered

- **A core, with `contrib/` for the rest** (`detections/` there, labelled unvalidated). Rejected: it moves files
  without changing what they have shown, and the labels say the same thing without breaking paths.
- **Separate repositories** for the gate, the detections and the hardening script. Rejected: three CI and release
  processes for one maintainer, and both would still depend on the gate's IOC data and loader.
- **Retire WS-GH-003 and WS-GH-004 now,** leaving them to zizmor. Rejected for now: the overlap is from zizmor's docs,
  not measured; the corpus run in the ROADMAP decides it.
